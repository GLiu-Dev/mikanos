osbook_day03c 是 day03b 的下一个里程碑，核心变化就一句话：**引导程序不再自己负责"画完就完"，而是把帧缓冲区的基地址和大小作为参数传给内核，由内核（C++）自己绘制画面**。这是"MikanOS 第一个真正由内核驱动的图形输出"。

## 一、day03b → day03c 变化对比

| 维度 | day03b | day03c |
| --- | --- | --- |
| 内核入口签名 | `EntryPointType(void)`，无参数 | `EntryPointType(UINT64, UINT64)`，两个参数 |
| 跳转调用 | `entry_point()` | `entry_point(gop->Mode->FrameBufferBase, gop->Mode->FrameBufferSize)` |
| 谁画画面 | 引导程序全屏刷白（内核不画） | 引导程序仍刷白（本版本保留了该循环），随后**内核覆盖成渐变** |
| 内核职责 | 空转 | `KernelMain` 绘制渐变 + `hlt` 停机 |
| 数据交接 | 无（内核不知道显示信息） | 把**帧缓冲区物理地址 + 大小**交给内核 |

## 三、关键机制分析

**1. 为什么 `extern "C"`？**
C++ 有名字修饰（name mangling），`KernelMain` 会被改写成内部符号。引导程序跳转时靠 ELF 的 `e_entry` 直接定位入口，不经过名字解析——`extern "C"` 是为了**明确该函数采用 C 链接**，保证与引导程序一侧的调用约定语义一致，也方便后续用入口地址直接对接。事实上这里入口是"地址"而非"符号名"，`extern "C"` 主要是声明语义与 ABI 约定的正确性。

**2. 渐变 `fb[i] = i % 256` 到底显示什么**

- 像素格式为 32 位（每像素 4 字节），相邻字节恰是 R/G/B 三个通道；
- 字节 `i`、`i+1`、`i+2` 分别写 `i%256`、`(i+1)%256`、`(i+2)%256`——三个通道随 `i` 同步递增；
- 每 256 字节 = **64 像素一个周期**，色相连续旋转，形成彩虹色带；
- 由于 `i` 是整块帧缓冲的平铺字节索引（不是按行重置），色带会**跨行连续、呈斜向渐变**，而非水平条纹。

**3. `while(1) __asm__("hlt")` 的作用**
`hlt`（Halt）让 CPU 进入停机状态，降低功耗并等待中断。这里没有启用任何中断处理，所以 `hlt` 永远不会被唤醒，内核在此"永久待机"。这是内核最基本的空闲循环写法。

**4. 引导程序仍保留全屏刷白**
本版本 `main.c` 里那个 `frame_buffer[i] = 255` 的刷白循环仍在——它先验证帧缓冲区可直写，随后内核的渐变立即覆盖。到后续版本这一"临时刷白"才会被移除，只保留传参职责。

## 四、与 day03b 相比，设计意图的转变

|  | day03b | day03c |
| --- | --- | --- |
| 画面归属 | 固件引导程序 | **内核** |
| 交接内容 | 无 | **帧缓冲信息（地址+大小）** |
| 里程碑含义 | 点亮图形 | **建立"引导程序→内核"的参数传递接口** |

day03c 的价值不在"多画了个渐变"，而在于：**它确立了内核如何从引导程序获取硬件信息的标准方式**——通过入口函数参数传递。这为后续 day04 传入内存映射、day06 传入 ACPI 表等"内核需要更多引导期信息"的扩展铺平了道路。

## 五、可留意的点

- 入口函数指针的调用约定依赖"两侧同为 GCC 默认 ABI"这一隐含假设；若内核改用显式 `EFIAPI`/MS ABI 编译，参数会落在 RCX/RDX，与引导程序侧不一致而崩溃。这里能工作是因为两边一致，属于**脆弱但当前成立**的约定。
- `KernelMain` 没有返回值、永不返回，与 `EntryPointType` 的 `void` 声明匹配；若将来内核需要返回，签名需同步修改。
- 帧缓冲参数用的是物理地址，内核直接 `reinterpret_cast` 成指针访问——依赖**恒等映射**（物理=虚拟），尚未建立页表，这点与 day03b 的 `e_entry` 假设一致。
